# Design audit — 194 findings across 13 surfaces

Produced by a 13-agent parallel audit of the repository. Severity as judged by the auditing agent.


## HIGH

- **Design token and theming foundation (src/common/tokens.css, colors.css, resets.css, theme.js, colors.js)** · `src/common/colors.js`
  - A third, entirely theme-blind color system. `accentColors` and `uiColors` are ~140 hardcoded HSL strings with no dark-mode path, imported by 11 modules (panels/action_buttons.js 13 refs, edit_canvas/draw_edit_affordances.js 9, display_canvas/display_canvas.js 5, draw_paths.js 3, project_editor/navigator.js 2, edit_canvas/edit_canvas.js 2, context_characters.js 2, common/graphics.js 2, panels/card_path_point.js 1). Its hues do not even match the CSS layer: blue 198 vs token 212, purple 285 vs 268, green 125 vs 152, orange 20 vs 24, royal 220 vs 226, gray 198@40% sat vs 220@14%.
  - *why:* Two visual systems ship side by side at different hues and saturations, so panel chrome, nav and canvas affordances are measurably off-hue from every token-driven surface, and none of them react to dark mode. For a canvas-centric tool this is the most visible defect in the product.
  - *fix:* Freeze colors.js: forbid new imports. Extend CANVAS_TOKENS and the semantic layer to cover every case it serves (path-point fills, action-button states, nav accents), then migrate consumers file by file to getCanvasColors() or var() and delete accentColors/uiColors. Keep only the color-math helpers (parseColorString, rgbToHex, shiftColor, getColorFromRGBA, transparencyToAlpha).

- **Design token and theming foundation (src/common/tokens.css, colors.css, resets.css, theme.js, colors.js)** · `src/common/colors.css`
  - The stated exclusion of always-dark surfaces from ramp inversion does not work. The comment at lines 55-63 claims the always-dark pages 'deliberately do NOT appear here' so they keep light-mode ramp values, but the inversion is declared on `:root[data-theme='dark']` and the ramps themselves are composed on `:root`. Custom properties inherit, so in dark theme `#cross-project-actions__page` receives the inverted ramp anyway.
  - *why:* src/app/app-pages.css uses ~20 ramp references inside that always-dark page (`color: var(--gray-l90)`, `color: var(--gray-l80)`, `border-color: var(--blue-l15)`, `background-color: var(--purple-l15)`). With the ramp inverted, --gray-l90 resolves to hsl(220,11%,16%) - near-black text on a near-black ground. The page is unreadable for every user in dark theme, and the file comment actively misleads the next author into believing it is safe.
  - *fix:* Either re-declare the full light-mode `--l99`..`--l05` and `--sat-*` block on `#cross-project-actions__page` inside colors.css so the exclusion is real, or migrate that page off ramps to `--bg-surface`/`--text-primary`/`--border-default` and delete the exclusion comment. Do not leave the comment describing behavior the cascade does not produce.

- **Design token and theming foundation (src/common/tokens.css, colors.css, resets.css, theme.js, colors.js)** · `src/common/tokens.css`
  - The dark pre-paint fallback supplies no dark tokens. Lines 334-338 match `@media (prefers-color-scheme: dark)` but set only `color-scheme: dark` - not a single semantic token is redefined. The comment at lines 246-247 nonetheless calls it 'a pre-paint fallback for the moment before JavaScript runs'.
  - *why:* A system-dark user loads the full light palette (--bg-app = --n-06, near-white) and holds it until theme.js runs initTheme(). That is a full-screen white flash on every load and every hard refresh, which is exactly the failure theme.js's localStorage-first design was built to avoid. It also makes the comment a false statement a future author will trust.
  - *fix:* Either duplicate the dark semantic block under `@media (prefers-color-scheme: dark) :root:not([data-theme='light'])`, or inline a blocking script in index.html <head> that reads localStorage and stamps data-theme before first paint. Then correct or delete the comment.

- **Design token and theming foundation (src/common/tokens.css, colors.css, resets.css, theme.js, colors.js)** · `src/project_editor/pop_out_window.js`
  - The pop-out window loads `colors.css?inline`, `resets.css?inline`, `dialogs.css?inline`, `panels.css?inline` and `pop-out-window.css?inline`, but never tokens.css. Confirmed: no reference to 'tokens' anywhere in the file.
  - *why:* Everything resets.css and panels.css draw resolves against tokens that do not exist in that document: --text-primary, --bg-app, --fs-md, --control-h-sm, --border-strong, --r-xs, --shadow-1, --transition-color. Every one falls back to the initial value, so the pop-out live preview renders unstyled text on a transparent ground. colors.css's own aliases (--accent-color: var(--accent)) are dead there too. A pop-out preview is a core workflow for a font tool.
  - *fix:* Import `tokens.css?inline` first in pop_out_window.js and inject it ahead of colorStyle, and mirror the host document's data-theme onto the pop-out's documentElement plus subscribe via onThemeChange so the pop-out follows theme switches.

- **Design token and theming foundation (src/common/tokens.css, colors.css, resets.css, theme.js, colors.js)** · `src/controls/dialogs/dialogs.css`
  - No z-index scale exists in the token layer. 15 sites hand-pick values: 2 (panels.css:1030), 5 and 10 (editor-pages.css:147,54,292), 100 (app-pages.css:470, nav.css:120), 1000 (dialogs.css:2), 2000 !important (app.css:27), 2000 (dialogs.css:268), 2010 (dialogs.css:18, info-bubble-popup.css:11), 2020 (dialogs.css:48), 2030 (dialogs.css:124), 3000 (command-palette.css:12 and a template literal in edit_canvas/events_keyboard.js:506).
  - *why:* The stacking order is undocumented and already contested - app.css:27 needs `!important` at 2000 to win against a dialog layer at the same number, and a raw 3000 is duplicated between a stylesheet and a JS string. In a tool with modals, popovers, a command palette, toasts and canvas overlays, every new floating surface is a guess that will eventually land behind something.
  - *fix:* Add a --z-* scale to the component layer (--z-base 0, --z-canvas-overlay 10, --z-sticky 100, --z-dropdown 1000, --z-modal-backdrop 2000, --z-modal 2010, --z-popover 2020, --z-toast 2030, --z-command-palette 3000), replace all 15 sites, and delete the !important at app.css:27.

- **Reusable control library — src/controls/*** · `src/controls/tabs/tab-control.css`
  - Line 21 reads `outline: var(--global-outline-style)`. That custom property is used in exactly this one place and is defined nowhere in the codebase — resets.css:3 defines `--global-focus-style`, not `--global-outline-style`.
  - *why:* The declaration is invalid at computed-value time, so tab elements get no focus ring whatsoever. A whole navigation surface is invisible to keyboard users, and the bug is silent — nothing in the build or the browser console reports it.
  - *fix:* Replace with `outline: var(--focus-style); outline-offset: var(--focus-offset);` under `:focus-visible`. Then grep the repo for every `var(--…)` that has no `:root` definition and fix the rest the same way.

- **Reusable control library — src/controls/*** · `src/controls/dialogs/dialogs.css`
  - `.context-menu-row` is `display: contents` (line 142) yet the same rule sets padding, height and border-radius, and line 163 sets `.context-menu-row:focus { outline: var(--global-focus-style) }`. An element with display:contents generates no box, so all four are dead. Compounding this, dialogs.js gives each row `tabindex="0"` but binds only a `click` listener — a div does not fire click on Enter or Space.
  - *why:* The context menu is the app's primary command surface (right-click, File menus, and every option-chooser dropdown render through it). It is tab-focusable with no visible focus indicator and no way to activate a row from the keyboard. For a keyboard-first tool this is the single worst control in the library.
  - *fix:* Give each row a real box (`display: grid; grid-column: 1 / -1` with its own sub-grid, or make rows `<button>`), draw focus on `:focus-visible`, and add a roving-tabindex keydown handler: Up/Down/Home/End to move, Enter/Space to activate, Escape to close, plus role="menu"/"menuitem".

- **Reusable control library — src/controls/*** · `src/controls/glyph-tile/glyph_tile.js`
  - The tile's `.wrapper` is created with no tabIndex and the host element never receives one, so glyph-tile is unreachable by keyboard. glyph-tile.css nonetheless styles `.wrapper:focus`, and src/common/resets.css:318 lists `glyph-tile:focus-visible` — both are dead code written against a state that cannot occur.
  - *why:* The character grid is the main navigation surface of a font editor and it is mouse-only. Arrowing through glyphs is the single most repeated action a type or game designer performs.
  - *fix:* Set `tabIndex: 0` on the host (not the shadow wrapper, so the resets.css rule applies), add role="gridcell"/aria-selected, and implement arrow-key roving focus plus Enter to open in the grid container that owns the tiles.

- **Reusable control library — src/controls/*** · `src/controls/dialogs/dialogs.css`
  - `#modal-dialog` (line 270) paints its scrim as literal `rgba(255, 255, 255, 0.75)`. Meanwhile src/controls/command-palette/command-palette.css:17 paints its scrim as literal `hsla(220, 25%, 6%, 0.45)`. Neither is a token, and they are opposite colors. Separately, makeModalDialog() builds a `<dialog>` element that is appended to document.body and never has .showModal() called on it.
  - *why:* In dark theme every modal flashes a 75%-white sheet over the canvas — the most jarring thing the app can do to someone editing outlines at night. And because .showModal() is never called there is no focus trap, no inert background and no native Escape; tabbing out of a modal silently lands on the page behind it.
  - *fix:* Add `--scrim` to tokens.css (one value per theme), use it for both overlays, and switch showModalDialog to `dialog.showModal()` with `::backdrop` styling.

- **Reusable control library — src/controls/*** · `src/controls/input-number/input-number.css`
  - The host is `height: var(--control-h-sm, 26px)` (line 39), which resolves to the token's 24px — but its own `.arrowWrapper` is hardcoded `height: 26px` with `grid-template-rows: 13px 1px 12px` (lines 100, 104) and `.lock` is `max-height: 26px` (line 205). Across controls the drift is worse: option-chooser and option-toggle compute to 26px (24px .selection-display + 1px borders), the command palette row is `--control-h-lg` 32px, a context-menu row is `--row-h` 28px, and fancy-button declares no height at all.
  - *why:* The arrow stack overflows its own control by 2px, and a panel row containing a number field next to a dropdown next to a button cannot be made to align on any baseline. Dense inspector panels are where a font editor lives; misalignment at this scale is the first thing a designer sees and the hardest to unsee.
  - *fix:* Pick one control height (28px, `--control-h`) for every inline form control, delete the 26px literals, derive the arrow rows from it with calc(), and give fancy-button an explicit height from the same token.

- **Reusable control library — src/controls/*** · `src/controls/info-bubble/info_bubble.js`
  - show() and hide() (lines 93-95 and 116-118) assign colors directly as inline styles: `entryPoint.style.borderColor = 'rgb(180, 180, 180)'`, `.backgroundColor = 'rgb(180, 180, 180)'`, `.color = 'rgb(250, 250, 250)'`. The same literals are repeated in info-bubble.css lines 30-32. info-bubble.css:24 also sets `.wrapper:focus { outline: 0 }`.
  - *why:* Inline styles outrank any stylesheet, so this control can never be themed — it will stay mid-grey in dark mode no matter what tokens.css does — and it deliberately deletes its own focus ring. The 12×12px '?' target is also half the minimum comfortable hit size.
  - *fix:* Delete the inline style writes; toggle an `[open]` attribute on the entry point and drive border/background/color from `--icon-default`, `--bg-hover` and `--text-inverse` in CSS. Remove `outline: 0` and restore the focus-visible ring. Grow the hit area to 24×24 with transparent padding around the 12px glyph.

- **Reusable control library — src/controls/*** · `src/controls/option-chooser/option-chooser.css`
  - No control in src/controls uses `:focus-visible`, and focus is drawn six mutually incompatible ways: option-chooser has no outline at all (lines 18-19 only share the hover border-color); option-toggle and input-number use `outline: var(--global-focus-style); outline-offset: -1px`; fancy-button uses the same outline with no offset; tabs use an undefined token; info-bubble and font-preview explicitly set `outline: 0` / `outline: none`; context-menu rows draw an outline that cannot render. The one correct rule exists at src/common/resets.css:308 but cannot cross a shadow boundary.
  - *why:* Focus is the only feedback a keyboard-first tool gives about where you are. Six treatments means there is no system, and the two most common controls (dropdown, button) disagree with each other. On `:focus` rather than `:focus-visible`, every mouse click also leaves a ring behind — the opposite of calm.
  - *fix:* Define one shadow-DOM-safe snippet — `:focus-visible { outline: var(--focus-style); outline-offset: var(--focus-offset); border-radius: var(--r-xs); }` — and paste it verbatim into every control stylesheet. Ban bare `:focus` styling and any `outline: 0`.

- **Application shell and navigation (top bar, page switching, project hub vs. editor, multi-project, pop-out window)** · `src/app/app.css`
  - `#app__main-content { min-width: 720px }` (line 33) sits inside `#app__wrapper { overflow: hidden }` (line 10), so below 720 CSS px the app is silently clipped with no scrollbar and no reflow.
  - *why:* 200% browser zoom on a 1366px laptop yields 683 CSS px, and 200% on 1280px yields 640 — the most common accessibility zoom level cuts the right edge of the app off with no way to reach it. The top bar itself is a sibling grid child and keeps shrinking, so the bar and the content below it also fall out of alignment.
  - *fix:* Remove `min-width: 720px`. Make the shell reflow to ~640 CSS px (collapse the top-bar menus into one overflow button, let editor panels become overlays). If a hard floor is genuinely needed, put `overflow: auto` on the content row so the clipped area is at least reachable — never clip.

- **Application shell and navigation (top bar, page switching, project hub vs. editor, multi-project, pop-out window)** · `src/app/app.js`

- **Application shell and navigation (top bar, page switching, project hub vs. editor, multi-project, pop-out window)** · `src/app/open_project.js`

- **Application shell and navigation (top bar, page switching, project hub vs. editor, multi-project, pop-out window)** · `src/app/app.js`
  - The app has no unsaved/dirty state. A grep for `unsaved|dirty` across src returns only the settings label in src/pages/settings_data.js:183 and the `onbeforeunload` string at line 372. Autosave fires silently from src/project_editor/history.js:107-112, and `showBeforeUnloadConfirmation` is gated on a *setting*, not on whether anything actually changed.

- **Application shell and navigation (top bar, page switching, project hub vs. editor, multi-project, pop-out window)** · `src/app/app-pages.css`
  - Full-window app pages are positioned by cancelling a grid row with a negative offset: `#open-project__page { position: relative; top: calc(var(--topbar-h) * -1); height: 100vh }` (line 12) and `#cross-project-actions__page { top: -40px; height: 100vh }` (line 600). - **External standards (Apple HIG + modern browser design tools) applied to Glyphr Studio 2** · `C:/Users/varca/Documents/Bluerain/glyphr_studio_2/src/controls/dialogs/dialogs.css:8`
  - Dialog surfaces use a fixed width: 300px, info-bubble-popup.css:37 sets min-width: 300px, and the only layering policy in the codebase is bare z-index values (5 and 10 in editor-pages.css, ad hoc elsewhere). There is no documented rule for which transient surface may cover which.
  - *why:* Apple's rules here are hard rules, not preferences: show one popover at a time, never cascade popovers, allow nothing above a popover except an alert, and never show two alerts at once or a second modal before the first is dismissed.
